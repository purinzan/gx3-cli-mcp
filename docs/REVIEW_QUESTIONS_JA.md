# 変更を出す前に、コードに聞く8つの問い

このファイルは、**自分のテストではなく自分のコードに質問する**ための手順です。
変更を書き終えたあと、PR を開く前に、上から順に実行してください。

## なぜこれが要るのか

このプロジェクトで見つかったバグは、はっきり2種類に分かれます。

**動かすと自分から知らせてくるもの。** 例外で落ちる、遅すぎて終わらない、出力が
目に見えて壊れる。これは実行すれば見つかります。

**成功の形をしたもの。** 終了コード0、`checked`、検出0件、空の一覧。これは実行
しても見つかりません。テストも通ります。そして**このプロジェクトが相手にしている
のは、まさにこの型**です。ラダー解析で「該当なし」は「安全」と読まれるからです。

過去に見つかったものを並べると、後者は例外なく「コードを、そのコード自身が書いた
契約と突き合わせる」ことで出てきました。テストは自分が書いた検体で自分の実装を
確認するので、この型を構造的に見つけられません。

以下の問いは、実際にバグを出したものだけを載せています。理屈で思いついたものは
入れていません。

---

## 1. 宣言した状態・種別のうち、実際に構築されるのはどれか

語彙に並んでいるだけで、誰も作らない状態は「区別している」という主張の嘘です。

```bash
python - <<'PY'
import re, pathlib, collections
counts = collections.Counter()
for p in pathlib.Path("gx3cli").glob("*.py"):
    if p.name == "gx3_analysis_state.py":
        continue
    for m in re.finditer(r"AnalysisState\(\s*([A-Z_]+)", p.read_text(encoding="utf-8")):
        counts[m.group(1)] += 1
print(counts)
PY
```

構築ゼロの状態が出たら、**その状態が表すはずだった入力を実際に作って**、いま何が
返るか見てください。

> 実例: `UNSUPPORTED` は宣言・文書化・ロードマップの完了条件になっていて、構築箇所
> がゼロでした。LD 1本と FBD 1本のプロジェクトで `metrics` は `programs 1` と答え、
> FBD は存在ごと消えていました。

`NO_MEASUREMENT` は**いまも構築ゼロ**です。次に潰す候補です。

> 実例2: この問いを2周目に回したとき、`trace-device` が「このプロジェクトに存在しない
> デバイス」と「存在するが誰も書かないデバイス」を同じ答え
> （`driver_rows=0, truncated=False`）で返していたことが出ました。前者は打ち間違いか
> プロジェクト違いで、まったく別の話です。

## 2. 宣言したフラグで、既定値以外になる箇所があるか

**この検査が見るのは、構築後に代入される bool フラグだけです。** コンストラクタで渡されるフィールドは拾いません（型を広げるとノイズだらけになり、リスト全体が使われなくなります）。範囲を承知のうえで使ってください。

```bash
python - <<'PY'
import ast, pathlib, re
for p in sorted(pathlib.Path("gx3cli").glob("*.py")):
    try:
        tree = ast.parse(p.read_text(encoding="utf-8"))
    except SyntaxError:
        continue
    for node in ast.walk(tree):
        if not isinstance(node, ast.ClassDef):
            continue
        for item in node.body:
            if isinstance(item, ast.AnnAssign) and isinstance(item.target, ast.Name):
                if ast.unparse(item.annotation) != "bool":
                    continue
                field = item.target.id
                hits = sum(
                    1
                    for q in pathlib.Path("gx3cli").glob("*.py")
                    for i, line in enumerate(q.read_text(encoding="utf-8").splitlines(), 1)
                    if not (q == p and i == item.lineno)
                    and re.search(rf"\b{re.escape(field)}\s*[=:](?!=)", line)
                )
                if hits == 0:
                    print(f"{p.name}: {node.name}.{field} は宣言以外に代入なし")
PY
```

> 実例: `uncertain` は「範囲が確定できない」を表すために置かれ、**一度も True に
> なりませんでした**。`BMOV D300 D400 D10`（件数がデバイス）が `checked` として
> 返り、書込先は D400 の1件だけ、と断言していました。

## 3. 成功の形をした出力を返す入力は何か

`checked` / 終了コード0 / 検出0件 / 空一覧 を返す経路を列挙し、**それぞれについて
「間違ってそう返る入力」を作れるか**試してください。作れたらバグです。

> 実例: 別プロジェクトの xref を `change-impact` に渡すと、行なし・到達なし・終了
> コード0・`checked` を返していました。`open_xref_db` は入力指紋を検証する関数で、
> 呼んでいなかっただけです。

## 4. 上限・境界で、隠れたものが本当にあるか

上限に触れたことと、上限のせいで見えなくなったものがあることは別です。
**各上限について3点**（1つ足りない / ちょうど / 1つ多い）を必ず掃いてください。

> 実例1: 深さ1で M300 が消えるのに `checked` を返していた。
> 実例2: それを直したとき**逆に倒しすぎ**、深さ2で全件取れているのに `truncated`
> と言うようになった。完全な答えに `truncated` が付くと、読み手はその語を読まなく
> なり、本当に短い答えでも無価値になります。

空入力（`worst([])`）も境界です。ここも一度落ちました。

## 5. 「共通化した」と書いたなら、呼び出し側は本当にそれを使っているか

PR 本文の主張ではなく、呼び出し側のコードを読んでください。

```bash
grep -c "while frontier\|while queue\|frontier.append" gx3cli/*.py | grep -v ":0"
```

> 実例0: `trace-device` は駆動をコイルの役割だけで集めていたので、命令が書くワード
> デバイスには駆動行が1本もありませんでした。実プロジェクトで **16本が書いている
> デバイスが `driver_rows=0` / `truncated=False`**（＝完全な答え）でした。
>
> 実例1: 「探索を共通化した」と書いた PR で、共通化されていたのは**次の到達先を
> 取得する処理だけ**でした。`downstream` には独自の探索ループと上限判定が残って
> いました。
> 実例2: 2つの探索を統一したあと、**3つ目**（`graph --type device-flow`）に修正が
> 届いていませんでした。ブロック転送が書いたデバイスを「値の出所」と断言していました。

## 6. そのテストは実経路を通しているか、作り物で通しているか

**テストを通すために手作りのデータが要るなら、それは「未カバー」の合図です。**
緑にしないでください。

> 実例: `BMOV → MOV` の追跡テストが、xref に行を手で挿入していました。テストも CI
> も緑で、PR にも「対応済み」と書きました。実際には**命令の読取りから追跡までの
> 経路は一度も通っていません**でした。指摘されるまで気づかず、次の作業に進みました。

手作りデータのテストを残すなら、役割を明記してください（「記録側と独立に、探索側の
契約を固定する」など）。そのうえで、**実経路を通すテストを別に置く**こと。

## 7. 段階（stage）と次の手順は、実際の制約と合っているか

`decode` / `topology` / `semantics` / `reach` は、**次に何をすべきかを決めるため**に
分けています。合っていないと、読み手を無関係な場所へ送ります。

- 命令は読めたが条件式が畳めない → `topology`。`parse-gaps` に送らない
- 命令は読めたが範囲が実行時の値 → `semantics`。実機のそのデバイスを見る
- 読めなかった → `decode`。`parse-gaps`
- 上限で止まった → `reach`。上限を上げる

> 実例: 巨大条件式の打切りを `decode` として報告し、`parse-gaps` に案内していました。
> 解読に欠落は無いので、そこには何もありません。

## 8. PR 本文の主張を、自分の差分と突き合わせたか

開く直前に、本文に書いた「対応した」項目を1つずつ差分と照合してください。

> 実例: 「対応済み」と書いた項目のうち2つが、差分を読み返せば主張と食い違っていました。

## 使い方

- 変更を書き終えたら、1〜8を上から実行する
- 該当なしでも「見た」と分かるように、PR 本文に**残した制約**を書く
- 新しい型のバグが出たら、**再現条件と一緒にこのファイルへ追記する**。理屈で
  思いついた問いは足さない（守られない項目が増えると、リスト全体が読まれなくなる）
