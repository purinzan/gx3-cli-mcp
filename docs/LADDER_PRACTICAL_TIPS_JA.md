# ラダー実務 Tips — 既設設備の変更・保全で外しにくい基本

> GX Works3 を含む既設 PLC の改造・レビュー時に、人または AI が最初に見るための最小チェックリスト。  
> これは安全規格そのものではなく、保全性・切戻し性・誤動作防止を重視した実務上の指針。

## 1. 改造は「旧回路を残して切替」を基本にする

既設動作を維持したまま新ロジックを追加する場合は、変更フラグを使って旧・新を排他的にする。

```text
旧回路:  --[/ CHANGE_FLAG ]--[ 既存条件 ]--------( OLD_REQ )
新回路:  --[  CHANGE_FLAG ]--[ 新設条件 ]--------( NEW_REQ )
```

- `CHANGE_FLAG = OFF` : 既存回路
- `CHANGE_FLAG = ON`  : 新設回路
- 原則として OFF を既存動作側にして、初期値・切戻し先を明確にする。
- 搬送中、動作途中、ステップ途中で切り替えない。切替可能条件を Idle / Home 等に限定する。
- 改造フラグで安全条件や本来必要なインターロックまで迂回させない。

## 2. 実出力は「1か所で書く」

同じ Y や重要な状態ビットを複数箇所の `OUT` で駆動しない。条件が複数ある場合は内部リレーへ分け、最後に集約する。

```text
--[ 自動条件 ]----------------------------( AUTO_REQ )
--[ 手動条件 ]----------------------------( MANUAL_REQ )

--+--[ AUTO_REQ   ]--+--[ PERMISSIVE ]--[/ FAULT ]--( Y10 )
  +--[ MANUAL_REQ ]--+
```

- 物理出力は single writer を基本にする。
- `OUT` と `SET/RST` を同じデバイスへ混在させない。使うなら誰が状態を所有するかを明確にする。
- 二重コイルを「条件が同時成立しないから大丈夫」で済ませない。後から条件変更された時に壊れやすい。

## 3. 安全・許可条件は旧新共通の最終段に置く

旧回路と新回路で共通して必要な条件は、可能なら最終出力側にまとめる。

```text
RUN_REQUEST
    AND Safety_OK
    AND Interlock_OK
    AND NOT Fault
    -> Physical_Output
```

変更フラグは「どの制御要求を採用するか」の切替に使い、安全・設備保護条件を無効化する用途には使わない。

## 4. 既設設備では「自分の好み」より「既存の流儀」を優先する

改造時に無関係な箇所まで整理・リファクタリングしない。

- 既存のデバイス割付、命名、コメント形式、回路順序に合わせる。
- 新設回路は対象機能の近くへ置き、変更範囲を局所化する。
- 既存ロジックと新機能追加を同じ変更で混ぜすぎない。
- スキャン順序に依存している既設回路は、見た目だけで並べ替えない。

保全では「美しい回路」より「誰が見ても変更点と影響範囲が分かる回路」の方が強い。

## 5. 起動・停止・異常・復帰をセットで考える

正常動作だけ作って終わらせない。

最低限、変更ごとに次を確認する。

- PLC 電源投入直後は何が ON / OFF になるか。
- ラッチデバイスを使う必要が本当にあるか。
- 停電復帰後に勝手に再始動してよいか。
- 異常発生時にどの状態を保持し、どれを落とすか。
- Reset 後に途中工程へ復帰するのか、原点 / Idle へ戻すのか。

## 6. シーケンス途中で制御方式を切り替えない

旧ロジックと新ロジックが同じ設備を制御する場合、フラグだけを瞬時に切り替えると内部状態が一致しないことがある。

- 切替は停止・Idle・原点など明示した安全状態だけで許可する。
- 必要なら「今回サイクルで使用するモード」をサイクル開始時にラッチし、終了まで固定する。
- 旧側の自己保持、タイマ、カウンタ、ステップ番号が残った状態で新側へ渡さない。

## 7. PLC はスキャン順序で結果が変わることを忘れない

ラダーは単なる論理式ではなく、実行順序を持つプログラム。

- 同じデバイスへの後段書込みが前段結果を上書きし得る。
- `MOV`、`OUT`、`SET/RST` などの書込み先重複をクロスリファレンスで確認する。
- ワンスキャンだけ必要な処理には立上り / 立下りパルスを使い、常時成立条件の下へ直接置かない。
- JUMP / MC-MCR 等で「実際にどこが実行されるか」を分かりにくくしすぎない。

## 8. Auto / Manual / Jog は要求を分け、出力で合流させる

各モードから直接同じ Y を書くより、モード別の要求ビットを作る。

```text
AUTO logic   -> AUTO_REQ
MANUAL logic -> MANUAL_REQ
JOG logic    -> JOG_REQ

AUTO_REQ OR MANUAL_REQ OR JOG_REQ
    AND common interlocks
    -> Y
```

こうすると、どのモードが出力を要求しているか追跡しやすく、二重コイルも避けやすい。

## 9. コメントは「何をしているか」より「なぜそうしているか」を残す

接点や命令を見れば分かる説明だけでなく、変更理由と意図を書く。

良いコメント例:

```text
M100  改造回路切替  OFF=既存 / ON=新設
      サイクル停止中のみ切替可。問題時は OFF で旧回路へ切戻し。
```

特に残すべきもの:

- ON / OFF の意味
- デフォルト状態
- 切替可能条件
- 旧回路との関係
- 例外的なスキャン順依存
- インターロックを置いた理由

## 10. ダウンロード前の最小チェック

- [ ] 同一 Y / M / D への意図しない複数書込みがない
- [ ] `OUT` と `SET/RST` の競合がない
- [ ] 旧回路と新回路が同時に有効にならない
- [ ] 改造フラグ OFF で既存動作へ戻せる
- [ ] 安全・設備保護インターロックが旧新どちらにも効く
- [ ] シーケンス途中で切替できない
- [ ] 電源再投入・異常・Reset 後の状態を確認した
- [ ] Auto / Manual / Jog 全モードで出力競合がない
- [ ] クロスリファレンスで書込み先を確認した
- [ ] 変更点以外の既設回路を不用意に触っていない

### 位置づけ

上記資料には、二重コイル回避、コメント・命名・構造化、保守性、標準化などの根拠がある。一方、`既存回路=B接点 / 新設回路=A接点` のような改造フラグ運用は IEC や三菱固有の必須規則ではなく、既設動作を既定値として残し、切戻しを容易にするための実務上の設計パターンとして扱う。
